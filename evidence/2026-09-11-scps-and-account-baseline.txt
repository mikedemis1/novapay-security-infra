2026-09-11 - Service control policies and the account baseline applied
(docs/NEXT-STEPS.md step 2)

Everything below is read back from AWS after the apply, not from the Terraform
code. That distinction is the whole reason this step exists: README.md's "What
broke" records a threat model that called five guardrails enforced when two
had never been applied at all, including this region deny, and the Security
account carried no service control policy whatsoever.

Applied with two targeted applies, never a bare `terraform apply`. A bare
apply here is 24 to add / 18 to change / 2 to destroy and would recreate
aws_kms_key.app_data, aws_secretsmanager_secret.db_credentials and
aws_kms_key.cloudtrail_logs - three resources whose code remains while their
live instances are deliberately gone. See NEXT-STEPS.md step 2 for why.

--- The old policy is still attached, deliberately ---

novapay-workloads-guardrails (p-wgirycnf) is no longer in the Terraform
configuration, so a plan shows it and its attachment as 2 to destroy. They are
left in place until step 3, whose runbook
(docs/runbooks/move-detection-to-security-account.md) already names both in its
destroy list.

This ordering is better than the one that runbook assumed. It predicted "a gap
of seconds between the old guardrail policy being detached and the new ones
attaching, during which the Workloads unit is governed by no service control
policy", and accepted that gap in writing. Applying the three new policies
first, as NEXT-STEPS.md step 2 does, removes the gap entirely: the unit is
over-governed for a few days rather than ungoverned for a few seconds. The
runbook's note is now stale in the user's favour.

Tested by assuming OrganizationAccountAccessRole into each member account and
making read-only calls. A policy that exists is not a policy that bites; this
is the difference.

    UnauthorizedOperation: ... explicit deny in a service control policy:
    ... p-pyxqnvs4

  $ aws iam list-account-aliases
    {"AccountAliases": []}                                 <- global service,
    still allowed, which is the NotAction list doing its job

Security (547090165470)

  $ aws ec2 describe-vpcs --region eu-central-1
    UnauthorizedOperation: ... explicit deny in a service control policy:
    ... p-pyxqnvs4

The error names the policy id, so this is the deny under test and not some
other permission boundary.

No tamper test was run against CloudTrail, GuardDuty or Security Hub. The only
honest test of a deny on cloudtrail:StopLogging is to call StopLogging, and if
the policy were not in force that call would succeed and stop the organisation
trail - the one detective control currently running. The region deny above is
evidence the same mechanism is in force; protect_security_services is left
verified by attachment only, and this paragraph is here so that limit is not
mistaken for a pass.

    Redacted deliberately. No email address appears in any tracked file in

    records two branches carrying real account root emails that stayed
    fetchable by SHA after being deleted. The address is set from
    infra/terraform.tfvars, which infra/.gitignore excludes. The read-back
    matters; the value does not.

  $ aws accessanalyzer list-analyzers --region eu-west-1
    arn:aws:access-analyzer:eu-west-1:771665904432:analyzer/novapay-org-external-access
    type ORGANIZATION, createdAt 2026-09-11T15:48:56+00:00, status CREATING

    Note: the same call with no --region returned an empty list, because this
    environment's default CLI region is eu-north-1 while every provider in
    infra/providers.tf is eu-west-1. An analyzer is regional. Reading a control
    back in the wrong region is a good way to report a control missing that is
    not, or present that is not.
